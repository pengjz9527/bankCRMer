# OppMiningAgent · 商机挖掘智能体设计方案

> **版本**：v2.0 | **日期**：2026-07-27 | **状态**：已实现
>
> **v2.0 变更**：移除每日定时全量 LLM 挖掘，改为按需触发；新增 CustomerInsightAgent 洞察缓存增强输入（方案 B+）

---

## 一、业务诉求

### 1.1 核心痛点

银行客户经理日常需从海量管户中主动发现潜在营销机会。传统做法依赖：
- **人工经验**：凭记忆和直觉判断"该联系谁了"
- **规则推送**：产品到期、生日提醒、大额异动等单维度规则

**问题**：
- 规则只能发现"表面信号"（比如活期余额高），无法推断"深层意图"（比如客户为何不买理财）
- 客户经理精力有限（管户 200-500 人），无法逐一手工分析
- 错失最佳触达窗口（如竞品到期资金回流后 3-7 天是关键窗口）

### 1.2 核心价值

| 能力 | 规则引擎能做吗？ | AI 独特价值 |
|------|:---:|------|
| 识别"活期余额 >5万" | ✅ 能 | — |
| 理解"工资到账后快速转出 → 过水卡，需绑定理财留存" | ❌ 不能 | **多信号交叉推理** |
| 理解摘要"购房定金" → 按揭贷款需求 | ❌ 不能 | **语义理解** |
| 综合 AUM 下降 + 行为减少 + 长期无沟通 → 流失预警 | ❌ 不能 | **多因子综合判断** |
| 通过沟通记录分析客户提到的隐性需求 | ❌ 不能 | **非结构化文本挖掘** |

### 1.3 业务场景

| 场景 | 触发方 | 频率 | 说明 |
|------|:---:|------|------|
| **一键 AI 挖掘** | 客户经理 | 按需（手动触发）| 限制该经理管户范围，优先分析高 AUM 客户，实时流式反馈 |
| **洞察增强** | 系统（自动）| 每次挖掘时 | 自动注入 CustomerInsightAgent 洞察缓存，交叉验证提升置信度 |
| **商机浏览** | 客户经理 | 随时 | 按经理/客户/状态查询已生成商机列表 |

## 二、流程设计

### 2.1 核心流程（一键 AI 挖掘）

```
客户经理点击"AI 挖掘"
  │
  ├─→ POST /api/ai/opportunity/mining/stream    ← SSE 流式
  │     { "manager_id": "M001" }
  │
  ├─→ mine_on_demand(ctx, manager_id)
  │     │
  │     ├─→ 1. 查询该经理管户（按 AUM 降序取 top 6）
  │     │
  │     ├─→ 2. 去重：跳过近 24h 已生成商机的客户
  │     │
  │     ├─→ 3. 注入洞察缓存（方案 B+）
  │     │     每位客户 → query_customer_insight() → _insight_cache
  │     │     注入 change_signals / risk_level / risk_signals
  │     │
  │     ├─→ 4. 分批分析（4 人/批, deepseek-chat）
  │     │     每批完成后 → 推送 SSE 进度事件
  │     │
  │     ├─→ 5. 评估：confidence >= 0.6 保留, >= 0.7 高置信
  │     │     洞察信号一致时 confidence +0.05~0.10（交叉验证加分）
  │     │
  │     └─→ 6. 入库 + 返回结果
  │
  ├─→ SSE 推送事件:
  │     event: phase         → {"phase":"start", "total_customers":50, ...}
  │     event: batch_progress → {"batch":1, "customers":["张三","李四"], "batch_signals":3}
  │     event: done          → {"status":"completed", "signals":5, "highlights":[...]}
  │
  └─→ 前端接收 SSE → 流式显示挖掘进度 → 完成后展示商机列表
```

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|-------|------|------|
| **触发方式** | 仅按需触发（商机看板"AI 挖掘"） | 每日定时全量 LLM 调用成本高，且多数方法不要求每日扫描 |
| **分批大小** | 按需 4 人/批 | 平衡 token 消耗与分析质量 |
| **洞察增强** | 注入 CustomerInsightAgent 缓存（方案 B+） | 交叉验证提升置信度，洞察不存在时自动降级 |
| **去重策略** | 按客户 ID + 24h 窗口 | 避免重复挖掘浪费 API 额度 |
| **去重粒度** | 客户维度（同一客户 24h 内只挖掘一次）| 客户数据不会在一天内发生质变 |
| **进度反馈** | SSE 流式推送 phase / batch_progress / done | 让客户经理感知 AI 正在工作 |
| **模型选择** | deepseek-chat | 按需场景优先分析质量 |

## 三、技术设计

### 3.1 数据类定义

```python
@dataclass
class OpportunitySignal:
    customer_id: int            # 客户 ID
    customer_name: str          # 客户姓名
    opportunity_type: str       # 商机类型（如"活期沉淀盘活"）
    title: str                  # 一句话摘要（≤30字）
    confidence: float           # 置信度 0.0-1.0
    estimated_value: float      # 预估价值（万元）
    reasoning: str              # 推理链路（必填，自然语言）
    suggested_action: str       # 建议行动（含切入点和推荐方向）
    priority: str               # 高 / 中 / 常规
    source: str = "AI-opp_mining"  # 区分于规则推送
    source_method: str = ""     # 方法标识（如 method_1_current_deposit）
    trigger_signals: list       # 触发了哪些具体信号
```

### 3.2 核心类结构

```
OppMiningAgent (extends Agent)
├── system_prompt: "prompts/opportunity_mining.md"
├── adapter: ModelAdapter (deepseek-chat)
│
├── mine_on_demand(ctx, mid)    # 按需挖掘（唯一入口）
│   ├── query_customers(mid)    # 该经理管户
│   ├── _query_recent_opp()     # 24h 去重
│   ├── _analyze_batch()        # LLM 分析 (4人/批)
│   │   ├── query_customer_full()     # 组装原始数据
│   │   ├── query_customer_insight()  # 注入洞察缓存（方案 B+）
│   │   └── _build_user_prompt()      # 构建增强 prompt
│   └── 返回 highlights + all_signals
│
├── batch_mine_all(ctx)         # [已废弃 v2.0] 保留供批量回放
├── _analyze_batch(customers)   # 核心分析逻辑
│   ├── query_customer_full()   # 组装每位客户全维度数据
│   ├── _build_user_prompt()    # 构建 LLM user prompt（含洞察增强）
│   ├── adapter.analyze_json()  # 调用 LLM 强制 JSON 输出
│   └── _parse_batch_result()   # 解析 → OpportunitySignal 列表
│
└── _query_recent_opp_cust_ids()# 24h 窗口去重查询
```

### 3.3 数据上下文构建

每位客户组装的数据维度（精简策略减少 token）：

| 数据域 | 保留条数 | 用途 |
|--------|:---:|------|
| customer | 全部 | 基础画像 |
| family | 全部 | 家庭生命周期 |
| holdings | 全部 | 资产结构分析 |
| transactions | top 10 | 近期资金流向 |
| behavior_logs | top 5 | 近期行为偏好 |
| communications | top 3 | 近期沟通内容 |
| risk_assessment | current only | 风测结果 |
| risk_history | top 1 | 历史风测对比 |
| relations | top 3 | 关系图谱 |
| loans | 全部 | 信贷状况 |

### 3.4 Prompt 设计

System Prompt（`prompts/opportunity_mining.md`, 666 行）包含：

```
一、角色定义
  - 银行零售业务高级客户分析专家
  - 核心原则：宁缺毋滥、推理可解释、避免重复、多信号交叉

二、输入数据格式
  - JSON Schema 完整定义

三、挖掘方法（P0，12 条）
  每条方法包含：别称、触发信号、推理要点、置信度因子、输出示例
  + 方法1:  活期沉淀盘活
  + 方法2:  代发资金截留（过水卡识别）
  + 方法3:  他行资金归集（竞品资金截流）
  + 方法4:  大额异动 + AI 增强（资金性质推理）
  + 方法5:  AUM下降+活跃衰减 → 流失预警
  + 方法6:  他行转账增多 → 资金外流
  + 方法7:  子女教育 → 教育金/留学金融
  + 方法8:  退休临近 → 养老规划
  + 方法9:  职业变动 → 收入升级
  + 方法10: 风险偏好迁移 → 风险错配检测
  + 方法11: 转账摘要语义 → 消费意图
  + 方法12: 沟通记录 → 隐性需求信号

四、置信度评分规范
  - 基础分 0.5-0.7（命中信号数决定）
  - 调整因子（多方法交叉、客户等级、预估价值等）
  - 输出阈值：confidence >= 0.60

五、输出格式
  - JSON Schema 严格定义

六、约束与注意事项
  - 不重复系统推送、空结果允许、推理链路可读性、隐私保护
```

### 3.5 模型调用

```
LLM 调用方式:  adapter.analyze_json()
温度参数:      0.3（偏确定性）
强制 JSON:     response_format={"type": "json_object"}
防解析失败:    3 次修复尝试（移除尾随逗号、截断到完整 JSON）
```

## 四、调用设计

### 4.1 API 端点

| 端点 | 方法 | 说明 | 响应方式 |
|------|:---:|------|:---:|
| `/api/ai/opportunity/mining` | POST | 同步挖掘（返回完整结果）| JSON |
| `/api/ai/opportunity/mining/stream` | POST | SSE 流式挖掘（实时进度）| SSE |
| `/api/ai/opportunity/list` | GET | 查询已生成商机列表 | JSON |

### 4.4 Agent 间协作

```
CustomerInsightAgent ──(洞察缓存)──→ OppMiningAgent._build_user_prompt()
                                        │
                                        │ _insight_cache 注入
                                        ▼
OppMiningAgent ──(产出商机信号)──→ opportunities 表
                                    │
                                    ├──→ ScheduleAgent 读取 opp 类待办
                                    │    加入日程排程输入
                                    │
                                    └──→ BattlePkgAgent 引用商机信息
                                         opportunity_info 参数传入
                                         生成作战包时附上"关联商机"
```

### 4.5 监控告警

| 指标 | 阈值 | 说明 |
|------|------|------|
| 单次挖掘耗时 | > 120s | 可能导致前端 SSE 超时 |
| 单批 LLM 调用耗时 | > 30s | 模型响应异常 |
| 置信度 >= 0.7 信号占比 | < 10% | Prompt 或数据质量可能下降 |
| LLM JSON 解析失败率 | > 5% | 模型输出格式不稳定 |

# SchedulerAgent · 日程排程智能体设计方案

> **版本**：v2.1 | **日期**：2026-07-28 | **状态**：✅ 已实现
>
> **v2.1 变更**：ScheduleTask 新增 `channel_plans` 字段，支持渠道执行计划；任务收集流程新增渠道计划生成步骤。

---

## 一、业务诉求

### 1.1 核心痛点

银行客户经理日均需处理 8-15 项待办，涉及产品到期、大额异动、商机跟进、客户联络、报告编写等多类型工作。传统做法中：
- 客户经理每天早上手工编排当日工作计划，效率低下
- 缺少科学的优先级排序——容易先做简单的事，遗漏重要的事
- 不了解客户的联系时段偏好，在错误的时间打扰客户
- 无法区分触客型工作（需要客户在场）和非触客型工作（内务类）
- 周维度视角缺失——不知道哪些任务需要提前规划以避免堆积

### 1.2 核心价值

| 能力 | 传统方式 | AI 排程 |
|------|---------|--------|
| **任务分类** | 手工判断每项任务属性 | 19 类工作分类目录 + 自动归类 |
| **三卡片展示** | 扁平列表 | 客户待办 / 商机待办 / 工作待办 三卡片轮播 |
| **优先级排序** | 凭经验（容易主观偏差）| 规则引擎按优先级权重 + 紧急度动态计算 |
| **时段分配** | 随机分配 | 基于推荐时段 + 客户联系偏好加权 |
| **序列优化** | 无 | 同类型相邻、短任务优先、长任务后置 |
| **周计划** | 看不到未来 7 天 | 贪心分配算法，含溢出任务提示 |
| **LLM 微调** | 无 | 合并同客户任务、高价值提权、长任务间隔 |
| **客户偏好** | 凭记忆 | 客户画像中 contact_prefer 字段驱动 |
| **商机来源** | 人工标记 | AI 挖掘 + 规则匹配，统一写入 opportunities 表 |

### 1.3 业务场景

| 场景 | 触发方 | 频率 | 说明 |
|------|:---:|------|------|
| **每日自动排程** | 系统 | 每日 08:00 | 全量待办收集 → 分类 → 三卡片排程 → 入库 |
| **手动重新排程** | 客户经理 | 按需 | 添加/删除/调整任务后重新生成 |
| **AI 智能微调** | 客户经理 | 按需 | 基于 LLM 语义理解做智能优化 |
| **7 日周计划** | 系统/客户经理 | 每日 / 按需 | 未来 7 天任务分配预览 |
| **日历事件标记** | 前端 | 随时 | 按月查询每日事件摘要（正常/商机/报告/会议）|
| **客户处理记录** | 客户经理 | 随时 | 标记每个客户的联系方式（电话/微信/跳过）|
| **任务退回待办池** | 客户经理 | 按需 | 将日程中的任务放回待办池 |

### 2.2 规则引擎排程（6 步流水线）

```
generate_daily_schedule(tasks, manager_id, date)
  │
  ├─→ Step 1: _classify_tasks(tasks)
  │    将原始待办按工作分类目录归类
  │    计算每项预估耗时
  │    提取 deadline / pinned / contact_prefer / opp_id 等字段
  │
  ├─→ Step 2: _inject_fixed_work_tasks(tasks, date)
  │    注入固定工作待办：早会（上午）、晚会（下午）
  │
  ├─→ Step 3: 优先级排序
  │    sort by (-priority_weight, -estimated_duration_min)
  │    P0(100) → P1(75-80) → P2(50-60) → P3(30)
  │
  ├─→ Step 4: _group_into_cards(tasks)
  │    按 CARD_GROUP_MAP 将任务分入三卡片：
  │      customer（客户待办） / opportunity（商机待办） / work（工作待办）
  │
  ├─→ Step 5: _apply_card_capacity(grouped, date)
  │    按容量上限截断 + 时段分配 + 溢出推迟
  │    规则:
  │      - customer ≤ 10（含上午 ≤ 5、下午 ≤ 5）
  │      - opportunity ≤ 4
  │      - work: 早会(固定) + 晚会(固定) + 其他 ≤ 2
  │      - opportunity + work ≤ 6（跨卡片约束）
  │      - 溢出任务标记 pinned_date 为次日
  │
  └─→ Step 6: _optimize_sequence(morning/afternoon)
       同类型相邻、高优先级在前
       按 (-priority_weight, estimated_duration_min) 排序
```

### 2.3 任务收集（8 步联动）

```
query_tasks_for_schedule(manager_id, schedule_date)
  │
  ├── 1. 产品到期 (holdings.maturity_date 7天内)
  │      → TK_DUE_{cust_id}，priority_weight=100，可合并多客户
  │
  ├── 2. 贷款逾期 (loans.overdue_count > 0)
  │      → TK_OD_{cust_id}，priority_weight=80
  │
  ├── 3. 大额异动 (昨日转出 > 3万, top 3)
  │      → TK_BIG_{cust_id}，priority_weight=80
  │
  ├── 4. 联络超期 (14天无沟通, top 5)
  │      → TK_CT_{cust_id}，priority_weight=50
  │
  ├── 5. AI 商机 → 读取 opportunities 表
  │      (source='AI-opp_mining', status='待跟进', 7天内生成)
  │      → TK_OPP_{opp_id}，priority_weight=50-75
  │
  ├── 5b. 规则商机 ← 5 类规则从原始数据实时生成
  │      5b-1. 代发配置 (近7天工资入账)
  │            → TK_OPP_SAL_{cust_id}，priority_weight=60
  │      5b-2. 到期承接 (8-30天到期产品)
  │            → TK_OPP_DUE_{cust_id}，priority_weight=70
  │      5b-3. 流失预警 (AUM<5万, tier低)
  │            → TK_OPP_DEC_{cust_id}，priority_weight=55
  │      5b-4. 基金意向 (浏览基金≥5次但无持仓)
  │            → TK_OPP_FUND_{cust_id}，priority_weight=60
  │      5b-5. 大额配置 (AUM>10万, random 3)
  │            → TK_OPP_BIG_{cust_id}，priority_weight=65
  │      已存在同客户商机任务时跳过（避免重复）
  │
  ├── 6. 洞察预警 → 读取 customer_insights 表
  │      (risk_level=orange/red 或有变化信号)
  │      → TK_INS_{cust_id}，priority_weight=75
  │
  ├── 7. 附加 contact_prefer（批量查询客户联系偏好）
  │
  └── 8. 规则商机入库 → INSERT OR IGNORE INTO opportunities
        （设计原则：商机待办必须来源于 opportunities 表，不允许凭空生成）
        source='rule', source_method='schedule_gen'
        同时注入 opp_id 到任务 dict
  │
  └── 9. 渠道执行计划生成 → 为每个客户待办生成 ChannelPlan（v2.1 新增）
        查询 customer_channels 表获取客户渠道可触达状态
        基于信号类型→渠道匹配策略（见核心业务模型 §六）生成计划
        closed 渠道自动跳过，选择下一优先级替代渠道
        写入 channel_execution_plans 表
```

### 2.4 7 日周计划生成

```
generate_weekly_plan(tasks, manager_id, start_date)
  │
  ├─→ Step 1: 分类 + 计算有效权重
  │    effective_weight = priority_weight + urgency_boost
  │    urgency_boost = max(0, 7 - days_until_deadline) × 10
  │    （越临近 deadline 权重越高）
  │
  ├─→ Step 2: 按有效权重降序排列
  │
  ├─→ Step 3: 逐日贪心填充（7 天循环，每天容量 480min）
  │    for day_offset in 0..6:
  │      ├── 3a. 固定日期任务（pinned_date = day_date）
  │      ├── 3b. 到期任务（deadline ≤ day_date）
  │      ├── 3c. 灵活任务（无 pinned_date 也无 deadline）
  │      └── 3d. 三步填充: pinned → due → flexible
  │           容量不足时跳过当前任务，尝试后续更小的任务
  │           未分配的任务留到后续天继续尝试
  │
  ├─→ Step 4: 溢出任务 = 7 天后仍未分配的任务
  │
  └─→ Step 5: 生成 7 个 DailySchedule + overflow_tasks
```

### 2.5 LLM 微调流程

```
ai_refine_schedule(ctx, base_schedule)
  │
  ├─→ 1. 收集所有任务涉及的客户 ID（最多 20 人）
  │
  ├─→ 2. 获取客户画像摘要
  │    { id, name, tier, aum, contact_preference }
  │
  ├─→ 3. 构建 LLM prompt（三卡片结构）
  │    - 当前排程（任务列表 + 卡片分配情况）
  │    - 客户画像摘要
  │    - 调整方向：合并/提权/间隔/商机时间优化
  │
  ├─→ 4. LLM 返回 changes 数组
  │    [{"task_id": "TK_xxx", "action": "move_to_slot", "new_slot": "morning"},
  │     {"task_id": "TK_xxx", "action": "reorder", "new_order": 2}]
  │
  └─→ 5. _parse_refine_result() → 应用到日程 → 返回调整后的 DailySchedule
       如 LLM 返回 has_changes=false → 保持原日程
```

### 2.6 客户处理与待办池管理

```
process_customer_task(schedule, task_id, cust_id, cust_name, action, db)
  │  记录单个客户的处理方式 → INSERT INTO processing_records
  │  action: '电话联系' | '微信联系' | '跳过'
  │  不修改 schedule 状态 → 前端在所有客户处理完后调用 complete 接口

return_task_to_pool(schedule, task_id)
  │  将日程卡片上的任务放回 deferred_tasks
  │  → 前端可再次从待办池添加到日程

add_task_to_card(schedule, task_id, card_type, pending_tasks)
  │  从 pending 池手动添加任务到指定卡片
  │  校验：卡片容量、客户卡上下午分时上限、商机+工作跨卡约束
  │  → 自动选择可用时段
```

### 3.4 数据类定义

```python
@dataclass
class WorkTypeCatalog:
    """工作分类目录"""
    type_code: str              # "due" / "big_move" / ...
    type_name: str              # "产品到期"
    per_customer_minutes: int   # 单客户单待办处理时长（分钟）
    recommended_slots: list     # ["morning"] / ["morning","afternoon"]
    priority_level: str         # "P0" / "P1" / "P2" / "P3"
    priority_weight: int        # 权重分：P0=100, P1=80, P2=50, P3=30
    contact_methods: list       # ["phone","wechat"] / [] 非触客为空
    is_customer_facing: bool    # 是否为触客型工作
    grouping_supported: bool    # 是否支持多客户合并排程
    photo_required: bool        # 是否需要拍照留痕

@dataclass
class ScheduleTask:
    """日程任务"""
    task_id: str                # "TK_DUE_14"
    type_code: str              # 工作分类码
    type_name: str              # "产品到期"
    cust_id: int = 0            # 主客户 ID
    cust_name: str = ""
    summary: str = ""           # 任务摘要
    cust_count: int = 1         # 涉及客户数
    estimated_duration_min: int = 0
    contact_methods: list = field(default_factory=list)
    is_customer_facing: bool = True
    is_opportunity_task: bool = False
    assigned_slot: str = ""     # "morning" / "afternoon"
    order_in_slot: int = 0
    priority_weight: int = 30
    customer_ids: list = field(default_factory=list)
    customer_names: list = field(default_factory=list)
    status: str = "pending"     # pending / adjusted / completed / skipped
    # 7 日排程扩展字段
    deadline_date: str = ""     # 最晚处理日期
    pinned_date: str = ""       # 固定排程日期（不可移动）
    effective_weight: int = 0   # 动态有效权重
    contact_prefer: str = "不限定"  # 上午优先 / 下午优先 / 不限定
    opp_id: str = ""            # 关联的商机 ID（来源于 opportunities 表）
    channel_plans: list = field(default_factory=list)  # 渠道执行计划列表（v2.1 新增）

@dataclass
class ScheduleCard:
    """日程卡片 — 客户待办 / 商机待办 / 工作待办"""
    card_type: str              # "customer" | "opportunity" | "work"
    card_name: str              # "客户待办" | "商机待办" | "工作待办"
    morning: list               # 上午任务列表
    afternoon: list             # 下午任务列表

    @property
    def total_count(self) -> int  # 当前未完成任务数（不含已完成）
    @property
    def max_capacity(self) -> int # 卡片容量上限

@dataclass
class DailySchedule:
    """日排程 — 三卡片结构"""
    date: str                   # "2026-07-28"
    manager_id: str
    cards: list[ScheduleCard]   # 三张卡片
    deferred_tasks: list[ScheduleTask]  # 溢出推迟到明日的任务
    generated_at: str           # 生成时间 ISO
    version: int = 0            # 版本号（重排递增）
    source: str = "rule"        # "rule" / "llm_refined"

    @property
    def total_tasks(self) -> int   # 所有卡片未完成任务总数
    @property
    def total_minutes(self) -> int # 所有任务预估总分钟

@dataclass
class WeeklyPlan:
    """7 日周计划"""
    start_date: str             # 周起始日期
    manager_id: str
    days: list[DailySchedule]   # 7 天排程
    overflow_tasks: list        # 溢出未排入
    total_tasks: int
    total_minutes: int
    generated_at: str
    version: int = 0
    source: str = "rule"
```

### 6.4 关键设计决策

| 决策点 | 选择 | 理由 |
|-------|------|------|
| **核心算法** | 规则引擎为主，LLM 微调为辅 | 排程是确定性计算，LLM 只做语义层面的微调 |
| **三卡片结构** | customer / opportunity / work | 清晰区分触客、商机、内务三类工作 |
| **渠道执行计划** | 基于信号类型匹配 + 客户渠道状态过滤 | 自动生成 ChannelPlan，closed 渠道自动跳过（v2.1） |
| **客户待办容量** | ≤10 项（上午 ≤5、下午 ≤5） | 防止排程过载，分时上限确保上下午均衡 |
| **商机待办容量** | ≤4 项 | 商机需要深度跟进而非泛泛处理 |
| **工作待办容量** | ≤4 项（含早晚会固定2项） | 早晚会固定占2，其余工作报告类 ≤2 |
| **跨卡片约束** | opp + work ≤ 6 | 避免触客型工作被非触客型挤占 |
| **时段模型** | 仅分上午/下午，不精确到小时 | 给客户经理留下灵活调整空间 |
| **客户偏好** | contact_prefer 字段加权 | 尊重客户时间偏好，提升触达成功率 |
| **LSM 调整量** | 最多 3 项 | 避免过度调整破坏规则引擎的确定性优势 |
| **溢出处理** | 不丢弃，保留 deferred_tasks | 让客户经理知晓未排入的任务，可手动添加 |
| **商机来源** | AI 挖掘 + 规则匹配，统一写 opportunities 表 | 商机待办必须来源于商机表，保证数据一致性 |
| **新旧兼容** | load_schedule 自动检测 card_type | 平滑迁移旧版 flat 格式数据 |

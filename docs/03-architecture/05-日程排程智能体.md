# SchedulerAgent · 日程排程智能体设计方案

> **版本**：v1.0 | **日期**：2026-07-24 | **状态**：✅ 已实现

---

## 一、业务诉求

### 1.1 核心痛点

银行客户经理日均需处理 8-15 项待办，涉及产品到期、大额异动、商机跟进、客户联络、报告编写等多类型工作。传统做法中：
- 客户经理每天早上手工编排当日工作计划，效率低下
- 缺少科学的优先级排序——容易先做简单的事，遗漏重要的事
- 不了解客户的联系时段偏好，在错误的时间打扰客户
- 无法区分触客型工作（需要客户在场）和非触客型工作（内务类）
- 周维度视角缺失——不知道哪些任务需要提前规划以避免堆积

### 1.2 核心价值

| 能力 | 传统方式 | AI 排程 |
|------|---------|--------|
| **任务分类** | 手工判断每项任务属性 | 10 类工作分类目录 + 自动归类 |
| **优先级排序** | 凭经验（容易主观偏差）| 规则引擎按优先级权重 + 紧急度动态计算 |
| **时段分配** | 随机分配 | 基于推荐时段 + 客户联系偏好加权 |
| **序列优化** | 无 | 同类型相邻、短任务优先、长任务后置 |
| **周计划** | 看不到未来 7 天 | 贪心分配算法，含溢出任务提示 |
| **LLM 微调** | 无 | 合并同客户任务、高价值提权、长任务间隔 |
| **客户偏好** | 凭记忆 | 客户画像中 contact_prefer 字段驱动 |

### 1.3 业务场景

| 场景 | 触发方 | 频率 | 说明 |
|------|:---:|------|------|
| **每日自动排程** | 系统 | 每日凌晨 0:00 | 全量待办收集 → 分类 → 排程 → 入库 |
| **手动重新排程** | 客户经理 | 按需 | 添加/删除/调整任务后重新生成 |
| **AI 智能微调** | 客户经理 | 按需 | 基于 LLM 语义理解做智能优化 |
| **7 日周计划** | 系统/客户经理 | 每日 / 按需 | 未来 7 天任务分配预览 |
| **日历事件标记** | 前端 | 随时 | 按月查询每日事件摘要（正常/商机/报告/会议）|

### 2.1 总体架构：规则引擎 + LLM 微调


### 2.2 规则引擎排程（5 步流水线）

```
generate_daily_schedule(tasks, manager_id, date)
  │
  ├─→ Step 1: _classify_tasks(tasks)
  │    将原始待办按工作分类目录归类
  │    计算每项预估耗时
  │    提取 deadline/pinned/contact_prefer 等字段
  │
  ├─→ Step 2: 优先级排序
  │    sort by (-priority_weight, -estimated_duration_min)
  │    P0(100) → P1(75-80) → P2(50) → P3(30)
  │
  ├─→ Step 3: _allocate_slots(tasks)
  │    分配上午/下午时段
  │    基于: recommended_slots + contact_prefer 加权
  │    规则:
  │      - 客户偏好"上午优先"且上午未满 → 优先放上午
  │      - 客户偏好"下午优先"且下午未满 → 优先放下午
  │      - 同客户多任务 → 统一到同一时段
  │      - 上午容量 MAX_MORNING_TASKS=5
  │      - 下午容量 MAX_AFTERNOON_TASKS=5
  │
  ├─→ Step 4: _optimize_sequence(tasks)
  │    同类型相邻（减少切换成本）
  │    高优先级在前、短任务优先、长任务后置
  │
  └─→ Step 5: _apply_constraints(morning, afternoon)
  │    上午容量 240min (4h, 含缓冲)
  │    下午容量 240min (4h, 含缓冲)
  │    超量日志警告（不丢弃任务）
  │    数量上限截断
```

### 2.3 7 日周计划生成

```
generate_weekly_plan(tasks, manager_id, start_date)
  │
  ├─→ Step 1: 分类 + 计算有效权重
  │    effective_weight = priority_weight + urgency_boost
  │    urgency_boost = max(0, 7 - days_until_deadline) × 10
  │    （越临近 deadline 权重越高）
  │
  ├─→ Step 2: 按有效权重降序排列
  │
  ├─→ Step 3: 逐日贪心填充（7 天循环）
  │    for day_offset in 0..6:
  │      ├── 3a. 固定日期任务（pinned_date = day_date）
  │      ├── 3b. 到期任务（deadline ≤ day_date）
  │      ├── 3c. 灵活任务（无 pinned_date 也无 deadline）
  │      └── 3d. 三步填充: pinned → due → flexible
  │           容量不足时跳过当前任务，尝试更小的任务
  │           未分配的任务留到后续天继续尝试
  │
  ├─→ Step 4: 溢出任务 = 7 天后仍未分配的任务
  │
  └─→ Step 5: 生成 7 个 DailySchedule + overflow_tasks
```

### 2.4 LLM 微调流程

```
ai_refine_schedule(ctx, base_schedule)
  │
  ├─→ 1. 收集所有任务涉及的客户 ID（最多 20 人）
  │
  ├─→ 2. 获取客户画像摘要
  │    { id, name, tier, aum, contact_preference }
  │
  ├─→ 3. 构建 LLM prompt
  │    - 当前排程（任务列表 + 分配情况）
  │    - 客户画像摘要
  │    - 调整方向：合并/提权/间隔/商机时间优化
  │
  ├─→ 4. LLM 返回 changes 数组
  │    [{"task_id": "TK_xxx", "action": "move_to_slot", "new_slot": "morning"},
  │     {"task_id": "TK_xxx", "action": "reorder", "new_order": 2}]
  │
  └─→ 5. _parse_refine_result() → 应用到日程 → 返回调整后的 DailySchedule
       如 LLM 返回 has_changes=false → 保持原日程
```

### 3.1 工作分类目录（10 类）

```python
WORK_TYPE_CATALOG = {
    # ======== 触客型工作（8 类）========

    "birthday":    # 生日提醒      P2·50分   afternoon·10min/客 可合并·微信/电话
```

### 3.5 Prompt 设计

System Prompt（`prompts/scheduler.md`, 58 行）：

```
一、角色定义
  - 智能日程管理助手
  - 只做合理且有依据的微调，不做大规模重排

二、工作分类参考
  - 10 类工作的属性速查表

三、调整原则
  可以做:
    1. 合并同客户任务
    2. 高价值客户提权（AUM≥50万，最多提前 2 位）
    3. 商机待办时间优化（10:00-11:30 或 14:00-15:30）
    4. 长任务间隔（报告/会议后插短待办）
    5. 高价值生日提醒提权（AUM≥100万）
  不可做:
    1. 不重新分配所有任务
    2. 不改变任务总数
    3. 不编造客户偏好
    4. 不改变 P0 优先级顺序

四、输出格式
  {"has_changes": bool, "changes": [...]}
  每次调整 ≤ 3 项
```

### 4.3 前端调用

```javascript
// 加载指定日期日程
async function loadSchedule(date) {
  const resp = await fetch(`/api/schedule/${date}?manager_id=${currentManagerId}`);
  const { data } = await resp.json();
  renderSchedule(data);  // → 渲染 W9 日程视图
}

// AI 重新排程
async function regenerateSchedule(date) {
  const resp = await fetch(`/api/schedule/${date}/regenerate`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ manager_id: currentManagerId })
  });
  const { data } = await resp.json();
  if (data.source === 'llm_refined') {
    showToast(`AI 优化了 ${data.changes.length} 项`);
  }
  renderSchedule(data);
}

// 手动调整日程
async function adjustTask(date, taskId, newSlot, newOrder) {
  const resp = await fetch(`/api/schedule/${date}/adjust`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ task_id: taskId, new_slot: newSlot, new_order: newOrder })
  });
}

// 加载日历事件标记
async function loadMonthEvents(year, month) {
  const resp = await fetch(`/api/schedule/${year}/${month}/events?manager_id=${currentManagerId}`);
  const { data } = await resp.json();
  renderCalendarDots(data.events);  // → 日历上显示圆点标记
```

### 关键设计决策

| 决策点 | 选择 | 理由 |
|-------|------|------|
| **核心算法** | 规则引擎为主，LLM 微调为辅 | 排程是确定性计算，LLM 只做语义层面的微调 |
| **任务上限** | 上午 5 项、下午 5 项、全天 8 项 | 防止排程过载，保留缓冲时间 |
| **时段容量** | 上午/下午各 240min（含缓冲）| 4 小时有效工作时间 |
| **客户偏好** | contact_prefer 字段加权 | 尊重客户时间偏好，提升触达成功率 |
| **LLM 调整量** | 最多 3 项 | 避免过度调整破坏规则引擎的确定性优势 |
| **溢出处理** | 不丢弃，保留 overflow_tasks | 让客户经理知晓未排入的任务 |

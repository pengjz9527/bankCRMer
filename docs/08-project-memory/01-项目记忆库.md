## 一、项目总览

### 1.1 功能架构

易会办是一个面向客户关系管理与智能营销的工作台系统，核心功能包括：客户全维度画像（家庭/企业/财富/信贷/行为等）、商机挖掘与管理、作战包策划执行、KPI 业绩看板、AI 智能体（商机挖掘/作战包/客户洞察/日程排程）以及日程排程调度。

### 1.2 前端架构现状

项目前端当前采用单文件巨石架构（`prototype/workbench.html` 达 11,079 行 / 498KB），存在 HTML/CSS/JS 混写、全局变量泛滥、字符串拼接 DOM、零 TypeScript、零模块化、零构建工具等问题，已严重阻碍维护与功能扩展。新前端（`frontend/`）基于 Vue 3 + Vite + TypeScript 正在建设中。

### 1.3 运营智能体管理后台

管理后台采用独立桌面布局（`/admin` 路由），包含五大功能模块：
- **定时任务管理**：查看/暂停/恢复/手动触发定时任务
- **智能体配置管理**：管理所有 Agent 的配置参数
- **运行监测**：查看 Agent 调用日志和 Token 用量
- **费用分析**：大模型 API 调用成本统计
- **模型配置**：切换大模型提供商和模型名称

首页作为仪表盘聚合展示系统状态、关键指标和告警信息。

### 1.4 大模型配置

当前平台统一使用 **DeepSeek deepseek-v4-flash** 模型：
- API 端点：`https://api.deepseek.com/v1`
- 规格：284B 参数 / 13B 激活，Flash 轻量版
- 价格：Pro 的 1/12，生成速度 +60-85%
- 四个智能体（商机挖掘、作战包生成、客户洞察、日程排程）共享同一模型实例

大模型运行时采用全局单例模式（`ModelAdapter`），通过管理后台修改配置时重建单例实现热切换，**不支持**按智能体路由不同模型。

## 二、核心设计原则

### 2.1 商机待办必须来源于已存商机

所有商机待办必须来源于已创建的商机记录（`opportunities` 表）。通过 `query_tasks_for_schedule` 发现规则商机时，需先将该商机写入 `opportunities` 表并生成 `opp_id`，再基于此 `opp_id` 创建关联的商机待办任务，确保待办与商机数据的一致性和可追溯性。

### 2.2 所有智能体调用必须走日志记录

所有智能体（Agent）的调用都必须确保被记录运行日志和 Token 用量。实现方式是统一通过 `harness.invoke()` 方法进行调用。**禁止**直接调用智能体实例的方法，以保证每次调用在管理后台可观测。

### 2.3 新增智能体需在 app.py 显式导入并初始化

新增智能体必须在 `app.py` 中完成两个步骤才能在管理后台可见：
1. 在文件顶部 `import` 对应的智能体模块
2. 在 `main()` 函数中调用其创建/注册函数（如 `create_qa_agent()`）

否则即使智能体代码已实现注册逻辑，也不会被加载到系统中。

### 2.4 新旧数据格式兼容

处理新旧数据格式兼容时，不能依赖 JSON 解析失败或 KeyError 作为判断依据。必须显式检查数据结构特征（如数组首元素是否含 `card_type` 字段），对旧格式调用专用的转换函数进行映射升级，确保平滑迁移。

## 三、日程排程系统

### 3.1 二卡片架构（客户级聚合）

日程排程采用二卡片结构，一个客户 = 一条综合待办（含该客户全部事件和商机）：

| 卡片 | 容量上限 | 说明 |
|------|:---:|------|
| **客户待办** | ≤7 项（按客户数） | 上午 ≤4、下午 ≤3 |
| **工作待办** | ≤4 项 | 早晚会固定占 2，其他 ≤2 |

每个客户综合待办（`customer_synthesis`）包含该客户的所有子事件（sub_items）和关联商机（opp_ids），按客户维度聚合而非事件维度。

仅分配到上午/下午，不定义具体时间。超出容量的任务自动推迟至次日并进入"未安排待办"池。已完成任务不计入容量。

### 3.2 客户综合待办聚合规则

事件级任务在进入排程前按客户聚合为 `customer_synthesis` 类型：

- **聚合维度**：按 `cust_id` 分组，一个客户 = 一条综合待办
- **task_id 格式**：`TK_CUST_{cust_id}`
- **priority_weight**：取子事件最大值
- **summary**：拼接前 3 项 + "等 N 项"
- **sub_items**：包含所有子事件（type_code、type_name、summary、priority_weight）
- **opp_ids**：收集所有关联商机 ID
- **时长估算**：20min（基础）+ 每个子事件 10min

事件类型包括：产品到期（due）、大额异动（big_move）、贷款逾期（overdue）、生日提醒（birthday）、联络超期（contact_lapse）、信用卡待办（credit_card）、洞察预警（insight_alert）、商机（opp_*）等。

### 3.3 待办池过滤规则

从待办池添加任务时需根据操作面板进行过滤：
- 在**客户待办**面板操作时，仅显示客户待办类型列表（含 customer_synthesis）
- 在**工作待办**面板操作时，仅显示工作待办类型列表
- 点击顶栏"未安排待办"徽标时，显示全部类型

## 四、定时任务

### 4.1 当前生效任务

| 时间 | job_id | 任务名称 | 说明 |
|------|--------|---------|------|
| 每日 06:00 | `daily_insight_refresh` | 客户洞察批量刷新 | 为全行客户刷新洞察快照 |
| 每日 07:30 | `daily_data_tick` | 数据日推进 | 注入当日交易/行为/沟通模拟数据 |
| 每日 08:00 | `daily_schedule_gen` | 日程自动生成 | 为全行客户经理生成周计划与日排程 |
| 每日 08:30 | `daily_news_fetch` | 金融资讯抓取 | Tushare/新浪/东方财富 |
| 每日 08:30 | `daily_digest_gen` | 资讯摘要生成 | 基于抓取资讯生成摘要 |
| 每日 20:00 | `daily_review_gen` | 昨日回顾生成 | 生成客户经理昨日工作总结 |
| 每周一 08:00 | `weekly_insight_gen` | 客户洞察生成 | 周度客户洞察批量刷新 |

所有定时任务由 APScheduler 管理，在 FastAPI 启动时自动注册。

### 4.2 日志存储

执行日志统一存储在 `yihuiban_sim.db` 的 `task_execution_history` 表中，包含 `job_id`、`status`、`result_summary`、`error_msg`、时间戳等字段。后端提供 `/api/admin/scheduled-tasks` 接口返回各任务最近执行摘要，管理后台可直接查看。

### 4.3 展示规范

- 所有 `job_id` 必须映射为中文名称展示（定义见定时任务中文名称映射规范）
- 技术性字段（如 cron 表达式）必须转换为用户友好的中文描述（如 `cron[hour='7', minute='30']` → "每日 07:30"）
- 智能体配置管理页面首次进入时，自动缺省选中列表中的第一个智能体

## 五、编码规范

### 5.1 AdminLayout 宽度一致性

`.admin-content` 容器应设置 `overflow-y: scroll` 而非 `auto`，通过始终预留滚动条空间来避免因滚动条出现/消失导致的页面宽度抖动问题。

### 5.2 商机看板目标进度区动态化

商机看板（OppBoardCard）中的目标进度区必须与客户经理的业务目标动态关联：
- AUM 净增值、月度目标、进度条使用 `kpiStore` 加载的实际数据
- 剩余缺口通过 `Math.max(0, target - current)` 动态计算
- 转化率预留 ref 可对接历史数据
- 需获取商机数通过 `缺口 / 转化率 / 平均商机价值` 动态推算
- `gapValue` 使用实际目标值而非硬编码

### 5.3 话术风格切换

面谈主界面提供话术风格切换功能，支持在"口语化"与"专业化"两种风格间实时切换。该功能为前端独立实现，不影响后端数据结构。

## 六、开发实践

### 6.1 前端 API 集成验证

前端所有交互调用必须对接后端真实 API 并验证返回数据，**禁止**使用静态数据或 mock 数据，只有在端到端运行验证通过后才算完成。

### 6.2 多 API 并发调用

在需要同时获取多个独立资源时，使用 `Promise.all` 并发调用多个 API，避免串行等待。例如 `CustomerDetail.vue` 中并行请求 8 个接口，显著提升页面加载速度。

### 6.3 浮窗/弹出层边界约束

所有弹出层/浮窗必须限制在 APP 工作区边界范围内：
1. 容器层：`.phone-frame` 添加 `transform: translateZ(0)` 创建包含块
2. 渲染层：`van-popup` 等组件使用 `teleport=".phone-frame"` 渲染到容器内部
3. 裁剪层：`.phone-frame` 保持 `overflow: hidden` 实现视觉裁剪

### 6.4 定时任务中文名称映射

| job_id | 中文名称 |
|--------|---------|
| `daily_data_tick` | 日增数据引擎 |
| `daily_schedule_gen` | 日程自动生成 |

## 七、常见陷阱

### 7.1 API_BASE 为空导致请求被 Vite 捕获

将 `API_BASE` 设置为空字符串 `''` 后，前端 API 请求变为相对路径 `/api/...`，被 Vite dev server（8080 端口）接收，返回 SPA 的 HTML 页面导致 `res.json()` 解析失败。正确做法是直连后端：`const API_BASE = 'http://localhost:8008'`（后端已启用 CORS）。

### 7.2 ChromaDB 同名文件 ID 冲突

使用 ChromaDB 存储向量时，若多个文件中存在同名文件（如 `README.md`），仅用文件名生成 chunk ID 会导致 `DuplicateIDError`。解决方案是生成 ID 时包含文件的相对路径，确保全局唯一性。

### 7.3 scheduled_schedule_gen 步骤顺序错误

`scheduled_schedule_gen` 因步骤顺序错误导致执行失败：在 `_group_into_cards` 返回 list 后又重复调用 `_allocate_slots`，导致 list 被污染为 dict。修复方案：确保 `_group_into_cards` 返回的 list 不被后续调用覆盖。

## 八、智能体专项

### 8.1 商机挖掘 Agent（方案 B+）

- 采用方案 B+ 增强设计：在构建 prompt 时可注入 `CustomerInsightAgent` 生成的洞察缓存（`_insight_cache`），用于交叉验证提升置信度
- 已移除原有的每日 02:00 定时全量挖掘任务，改为**完全按需触发**（商机看板中点击"AI 挖掘"按钮）

### 8.2 作战包 Agent

- API 端点：`POST /api/ai/battle-package/generate`
- 关键参数：`cust_id`、`mode`（电话版/面谈版）、`opp_id`、`opportunity_info`
- 响应特征：`bp_id` 前缀为 `BP_AI_`，生成耗时约 20-25 秒
- 前端适配：需显示三阶段加载提示（加载数据 → 匹配产品 → AI 生成中）

### 8.3 客户洞察 Agent

- 核心技能 `transcribe_dictation`：面访结束事件触发，客户经理口述 → AI 语音转写 → LLM 提取 PDCA 结构化信息 → 回填商机记录 → 更新客户画像（变更标红）→ 生成待办
- PDCA 提取内容：P（目的达成）、D（执行偏离）、C（客户反馈）、A（后续动作）

### 8.4 内容生成 Agent

- 支持定时触发和按需触发两种方式
- 计划任务：每日 08:30 生成资讯摘要、每日 20:00 生成昨日回顾草稿、每周一 08:00 协作生成周报
